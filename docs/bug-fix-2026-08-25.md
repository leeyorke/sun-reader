# Bug 修复记录：Git 历史中的大文件导致推送被拒

> 日期：2026-08-25
> 影响：`git push` 被 GitHub 拒收，无法发布代码
> 关键词：GH001、pre-receive hook、历史重写、filter-branch、gc

## 一、问题现象

推送时被远端拒绝：

```
remote: error: GH001: Large files detected.
remote: error: File node_modules/.pnpm/electron@28.3.3/.../electron.exe is 168.62 MB;
        this exceeds GitHub's file size limit of 100.00 MB
 ! [remote rejected] main -> main (pre-receive hook declined)
```

诡异之处：当前代码里**根本没有**追踪任何 node_modules 文件（早已加入 `.gitignore`），为什么还会报大文件？

## 二、根因分析

GitHub 的 100MB 文件限制检查的是**这次推送包含的全部 Git 对象**，而不仅仅是最新一次提交。

本项目的实际历史：

| 提交 | 发生了什么 |
| --- | --- |
| `init`（早期） | ❌ 误将整个 `node_modules/` 纳入追踪，electron.exe（168MB）进入对象库 |
| `移除node_modules的git追踪` | 从索引移除并添加 `.gitignore` —— **但旧对象仍留在之前的提交里** |
| 后续所有提交 | 干净 |

关键认知：

1. **`git rm --cached` / `.gitignore` 只影响现在和将来**，不会清除已经写进历史提交的对象。
2. 推送是按"远端缺失的提交区间"整体传输的。远端停在最初几个提交，所以这次要把**整段含大文件的历史**都传上去 → pre-receive 检查直接拒绝。

## 三、诊断三步

```bash
# 1. 找出哪些提交包含这个大文件
git log --all --oneline -- "node_modules/.pnpm/electron@28.3.3/node_modules/electron/dist/electron.exe"

# 2. 看远端停在哪（确认推送范围）
git ls-remote origin main

# 3. 列出全历史中最大的对象（通用排查，不限于已知文件）
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | Where-Object { $_ -match '^blob' } \
  | Sort-Object { [long]($_ -split ' ')[2] } -Descending | Select-Object -First 10
# Linux/macOS 把 Where-Object/Sort-Object 换成 grep '^blob' + sort -k3 -nr | head
```

## 四、修复步骤

### 第 1 步：从全部历史中剥离 node_modules

```bash
git filter-branch --force \
  --index-filter 'git rm -r --cached --ignore-unmatch node_modules' \
  --prune-empty \
  -- --all
```

- `--index-filter`：只改索引不动工作区文件，速度远快于 `--tree-filter`
- `--ignore-unmatch`：某些提交本来就没有该路径时不报错
- `--prune-empty`：剥离后变空的提交（如本项目那个纯加依赖的 init）自动删除
- 效果：10 个提交 → 9 个，所有 hash 重写

> 更现代的工具是 [`git filter-repo`](https://github.com/newren/git-filter-repo)（需额外安装），语法更安全；仓库小、一次性操作用内置的 filter-branch 足够。

### 第 2 步：删除备份引用 ⚠️ 最容易漏的一步

`filter-branch` 会把旧历史保存在 `refs/original/*` 下——**不清掉它，旧的大文件对象依然被引用着，gc 也删不掉**：

```bash
git for-each-ref --format='%(refname)' refs/original \
  | ForEach-Object { git update-ref -d $_ }   # bash: xargs -n1 git update-ref -d
```

### 第 3 步：过期 reflog 并强制回收对象

```bash
git reflog expire --expire=now --all
git gc --prune=now --quiet
```

### 第 4 步：验证

再次执行诊断第 3 步的"最大对象"扫描，确认只剩正常业务文件（本项目清理后最大的是 736KB 的应用图标），同时观察 `.git` 目录体积：

```
清理前：162.7 MB  →  清理后：1.1 MB
```

### 第 5 步：强推覆盖远端

历史 hash 全部变了，普通 push 必然冲突，需要覆盖：

```bash
git push --force origin main
```

## 五、注意事项

1. **force push 会覆盖远端分支**。动手前先 `git ls-remote origin main` 确认远端没有别人领先的工作；多人协作仓库应先周知。
2. **其他克隆副本会失联**：重写后旧 clone 里 pull 会混乱，协作者需要重新 clone 或 `git fetch && git reset --hard origin/main`。
3. **本次没用 Git LFS**：LFS 适合"确实要版本化管理的大文件"（设计稿、数据集）；node_modules 属于不该进版本库的东西，正确做法就是清历史而不是换存储。
4. **预防大于修复**：新项目第一次 commit 前就放好 `.gitignore`（node_modules、构建产物、大二进制）；一旦大文件进了共享历史，修复成本会高一个数量级。

## 六、命令速查表

| 目的 | 命令 |
| --- | --- |
| 找大文件所在提交 | `git log --all --oneline -- <path>` |
| 列全历史最大对象 | `git rev-list --objects --all \| git cat-file --batch-check=... \| sort` |
| 从历史删除目录 | `git filter-branch --index-filter 'git rm -r --cached --ignore-unmatch <dir>' --prune-empty -- --all` |
| 删除备份引用 | `git for-each-ref --format='%(refname)' refs/original \| xargs -n1 git update-ref -d` |
| 彻底回收对象 | `git reflog expire --expire=now --all && git gc --prune=now` |
| 覆盖远端 | `git push --force origin main` |
