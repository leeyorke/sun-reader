# Sun Reader React 重构方案

## 一、现状分析

### 当前架构
- **技术栈**: Electron + 原生 HTML/CSS/JS (多页面架构)
- **主进程**: main.js (501行) - 窗口管理、文件系统、IPC通信
- **预加载**: preload.js (65行) - 安全IPC桥接
- **渲染进程**: 4个HTML页面 + app.js (799行) + styles.css (1397行)
- **数据存储**: JSON文件 (~/SunReader/library.json, settings.json)

### 核心功能模块
1. **书库管理**: 书籍导入、删除、元数据管理
2. **阅读器**: 标准/沉浸/双页三种阅读模式
3. **阅读设置**: 主题切换(light/dark/sepia)、字体大小调整
4. **导航**: 翻页、进度追踪、目录
5. **批注**: 标记、笔记(部分实现)
6. **搜索**: 全文搜索(当前页)

---

## 二、重构目标

### 技术目标
- 迁移到 **React 18** + **TypeScript** 单页面应用(SPA)
- 保持 **Electron** 主进程架构不变(IPC通信、文件系统)
- 引入现代UI组件库和状态管理方案
- 实现响应式设计和更好的可访问性

### 功能目标
- 保留所有现有功能
- 改进阅读体验(更流畅的翻页、更好的排版)
- 增强书库管理(搜索、筛选、排序)
- 完善批注系统

## 五、关键技术决策

### 5.1 为什么选择这些技术?

| 技术 | 选择理由 |
|------|----------|
| **React 18** | 成熟的生态系统，Concurrent Features提升性能 |
| **TypeScript** | 类型安全，更好的IDE支持，减少运行时错误 |
| **Vite** | 快速的开发服务器，优化的生产构建，对Electron友好 |
| **Tailwind CSS** | 原子化CSS，快速开发，易于维护，Tree-shaking友好 |
| **shadcn/ui** | 基于Radix UI的无头组件，完全可定制，无样式锁定 |
| **Zustand** | 轻量级状态管理，无样板代码，支持TypeScript |
| **TanStack Query** | 强大的数据获取、缓存、同步机制，减少 boilerplate |

### 5.2 保留 Electron 的原因

1. **现有投资**: 主进程代码已经成熟，IPC通信机制完善
2. **原生能力**: 需要访问文件系统、对话框、原生菜单等
3. **分发成熟**: electron-builder配置完善，支持多平台打包
4. **迁移成本**: 迁移到Tauri需要重写主进程为Rust，成本过高

## 七、风险评估与缓解策略

### 主要风险

| 风险 | 影响 | 缓解策略 |
|------|------|----------|
| **重构周期过长** | 项目停滞，维护困难 | 分阶段实施，每阶段都有可工作的版本 |
| **功能遗漏** | 用户流失 | 编写详细的功能清单，逐个验证 |
| **性能下降** | 用户体验变差 | 使用React DevTools Profiler优化，对比原版本 |
| **TypeScript类型错误** | 开发效率降低 | 渐进式迁移，部分使用`any`过渡 |

---

## 八、总结

这份重构方案将 Sun Reader 从传统的 Electron + 原生 HTML/CSS/JS 架构迁移到现代化的 React 18 + TypeScript 技术栈，同时:

1. **保留核心资产**: Electron主进程逻辑基本不变，降低迁移风险
2. **采用最佳实践**: SPA架构、现代状态管理、类型安全
3. **分阶段实施**: 可控的迁移过程，每阶段都有可验证的产出
4. **功能完整保留**: 所有现有功能都有对应的实现方案

重构后的项目将具有更好的可维护性、开发体验和用户体验，为后续功能迭代奠定坚实基础。
